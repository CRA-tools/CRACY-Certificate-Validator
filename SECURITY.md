# Security policy

## Reporting a vulnerability

Please do **not** open a public issue for a security problem.

Report it privately through GitHub's [private vulnerability
reporting](https://github.com/CRA-tools/CRACY-Certificate-Validator/security/advisories/new) on this
repository. If that is unavailable to you, open a public issue that says only that you have a
security report and asks for a private contact — no details.

Please include, as far as you can:

- what the problem is and how it can be triggered,
- the version or commit you tested, and your OpenSSL version,
- the certificate material involved, if it can be shared safely — **never** send real private keys
  or customer certificates; a chain generated by `cracy-cert-generate` that reproduces the problem
  is ideal,
- what an attacker could achieve.

We aim to acknowledge a report within five working days and to agree a disclosure timeline with you.
Credit is given to reporters who want it.

## Scope

This is a local command-line toolkit that reads and writes files in the operator's own working
directory. It opens no ports, makes no network connections, and has no accounts or authentication.
Findings of the following kinds are expected rather than vulnerabilities:

- **Private keys written to disk in plaintext.** `cracy-cert-generate` writes the keys of the test
  CA it just created into `keys/`, unencrypted, because the invalidator needs them to re-sign
  certificates. This material exists only to be corrupted; it is not key material for anything real.
- **A PKCS#12 password passed as `--p12-password` is visible.** It appears in the shell history and
  the process list. This is documented, and `CRACY_P12_PASSWORD` exists as the safer alternative.
- **No revocation checking.** No CRL, OCSP or OCSP stapling; a revoked but unexpired certificate
  verifies. This is a documented limitation of scope.
- **No hostname or SAN matching.** The leaf is not checked against an expected identity.

In scope, and worth reporting:

- anything allowing code execution, path traversal or file disclosure on the host — including
  through a crafted certificate, container or filename that reaches an `openssl` invocation,
- a private key or PKCS#12 password leaking somewhere it should not: into a report, a log line,
  `DEBUG_CERT_CHAIN` output, or a temporary file that outlives the run,
- **an incorrect classification** — a chain reported `VALID` that should have been rejected, a
  severity that understates a trust failure, or a corruption scenario that silently produces a chain
  without the defect it claims. Wrong advice is the most damaging defect this toolkit can have, and
  a chain wrongly declared valid is treated with the same seriousness as a code vulnerability.

## Handling real certificate material

The toolkit is designed to be pointed at a product's real chain, and it makes no network connections
at any point, so material stays on the machine. Two things are worth knowing:

- The invalidator normalises any private keys it finds into a temporary directory in order to
  re-sign certificates. That directory is removed when the run finishes, including when a scenario
  fails.
- Output chains and reports are written into the working directory and are not cleaned up. They
  contain certificates, and generated chains contain keys, so treat the output directory with the
  same care as the input.
